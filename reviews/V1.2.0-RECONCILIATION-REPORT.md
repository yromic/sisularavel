## A. Scope & Objectives

### 1. Purpose of the Targeted Re-Audit
The **SISURAT Laravel Migration Contract Pack** was previously evaluated and given a conditional-readiness verdict due to several unresolved decisions, conflated requirements, and semantic contradictions. Because the contract pack will serve as the sole source of truth for an autonomous Laravel 13 development agent that will have **zero access** to the legacy Google Apps Script (GAS) codebase, Google Sheets, Google Drive, or legacy developers, all ambiguities and non-relational assumptions had to be resolved deterministically before repository transfer.

### 2. Core Corrections Addressed
1. **Letter Numbering Uniqueness:** Eliminating the conflation between external incoming letters and internal outgoing letters; defining explicit database DDL and constraints for both.
2. **Legacy Password Migration & Account Activation:** Deprecating insecure legacy credential formats (plain text and custom salted SHA-256); establishing zero-trust activation workflows (Path A Email, Path B Admin-assisted secret).
3. **Missing or Inaccessible Legacy Attachments:** Establishing durable database-level representation (`is_missing = true`, `migration_status` ENUM) for 404 Google Drive files to ensure letter metadata is never lost.
4. **Single-Division Ownership for v1:** Ratifying strict single-division ownership (`division_id`) and formally classifying inter-division routing as a deferred future feature.
5. **Server-Side Mutation Idempotency:** Augmenting client-side button disabling with mandatory server-side `Idempotency-Key` headers and database deduplication tracking.
6. **Review Semantics Reconciliation:** Correcting internal contradictions between audit defect priorities and readiness verdicts.
7. **Coverage Language Scoping:** Qualifying all "100% complete" claims with explicit numerators, denominators, source inventories, and audit boundaries.

## C. Incoming vs Outgoing Letter Numbering Findings & Contract

### 1. Incoming Letters Contract (`DEC-LET-001`, `BR-SM-003`)
- **Authoritative Identity:** The database primary key `id` (bigint unsigned auto-increment) is the sole authoritative record identifier.
- **No Database Unique Constraint:** There is **NO unique constraint** on `nomor_surat` or `(division_id, ..., nomor_surat)` for incoming letters. External institutions (e.g. BKD, Ministry of Education, local schools) assign letter numbers independently; collisions are legitimate.
- **Duplicate Advisory Detection:** The system performs an advisory duplicate check querying:
  $$\text{Query: } (division\_id = ?, asal\_surat = ?, nomor\_surat = ?, tanggal\_surat = ?)$$
- **Advisory Behavior:** If a matching record is detected, the UI displays warning `WARN_POTENTIAL_DUPLICATE_LETTER` requiring explicit operator confirmation ("Nomor surat dan pengirim serupa sudah terdaftar. Lanjutkan penyimpanan?"). Submissions with confirmation are stored cleanly.
- **Migration Consequence:** Legacy migration cleanly imports all incoming letters even when numbers collide across external senders.

### 2. Outgoing Letters Contract (`DEC-LET-002`, `BR-SK-002`)
- **Internal Authority:** Outgoing letters are issued internally by division administrators and staff.
- **Explicit Period Column:** The database schema introduces an explicit `letter_year` (smallint unsigned) column, populated via model observer / service layer from `YEAR(tanggal_surat)`.
- **Database Unique Constraint:**
  $$\text{UNIQUE KEY: } \text{outgoing\_letters\_div\_year\_num\_unique } (division\_id, letter\_year, nomor\_surat)$$
- **Historical Stability:** `letter_year` is derived directly from the formal letter date (`tanggal_surat`). Date modifications recalculate `letter_year`; if the new year creates a collision, the update is rejected with HTTP 422 (`ERR_422_DUPLICATE_OUTGOING_NUMBER`).
- **Required Indexes:** `INDEX (division_id, letter_year)` and `INDEX (letter_year)`.

## D. Authentication Migration & Password Activation Strategy

### 1. Approved Security Principle (`DEC-AUTH-001`, `BR-USER-003`)
Legacy passwords (plain text or custom salted SHA-256) are **strictly deprecated and rejected**. They will never be ported into Laravel password fields, verified via custom hash adapters, or accepted at login.

### 2. Migrated Account State
During migration from `db_users`:
1. Account identity, email, username, division, and role are imported.
2. `password` is set to a cryptographically secure, random, unusable Bcrypt hash.
3. `must_reset_password` is set to `true`.
4. Plaintext random secrets are never stored or displayed in migration logs.

### 3. Account Activation Lifecycles
- **Path A — Self-Service Activation via Verified Email:**
  - User requests reset on `/password/forgot`.
  - System generates a 60-minute single-use activation token in `password_reset_tokens`.
  - Notification sent via email. Audit log records `PASSWORD_RESET_REQUESTED` without token.
  - User submits new password (min 12 characters). System hashes with Bcrypt, clears `must_reset_password = false`, and invalidates token.
  - Endpoints protect against account enumeration using generic responses ("Jika email terdaftar, tautan aktivasi telah dikirim").
- **Path B — Admin-Assisted Activation (No Reliable Email Available):**
  - Authorized administrator clicks "Generate Kredensial Aktivasi" for a specific user in their division (`users:issue_activation_secret`).
  - Backend generates a single-use 16-character temporary secret, hashes it into `users.password`, and sets `must_reset_password = true`.
  - Secret displayed **once** in an administrative modal. Secret is transmitted via an approved out-of-band organizational channel (in-person memo).
  - Secret is **never logged** (`ADMIN_ISSUED_ACTIVATION_CREDENTIAL` records only actor and target user ID).
  - User authenticates with temporary secret $\rightarrow$ system intercepts `must_reset_password == true` $\rightarrow$ forces immediate redirection to `/password/activate` to establish permanent password.

## E. Durable Missing Legacy Attachment Handling

### 1. Approved Ingestion Principle (`DEC-FILE-003`, `BR-FILE-003`, `FILE-003`)
A legacy letter record must **never be dropped or discarded** solely because its referenced Google Drive attachment is missing (HTTP 404), inaccessible, or deleted.

### 2. Database-Backed Durability
In addition to generating a migration summary export (`missing_attachments.json`), durable state is persisted directly in the relational `attachments` table:
- `is_missing`: `boolean NOT NULL DEFAULT false`
- `file_path`: `varchar(255) NULL`
- `legacy_drive_url`: `text NULL` (preserves original Drive link for historical traceability)
- `migration_status`: `ENUM('migrated', 'missing_drive_file', 'inaccessible_drive_file', 'invalid_drive_url', 'download_failed', 'remediated') DEFAULT 'migrated'`

### 3. Operational & UI Behavior
- **Letter Detail View:** Renders full metadata normally. The attachment block displays an amber informational warning badge: *"Lampiran berkas warisan tidak tersedia di Google Drive saat migrasi"*.
- **Download / Preview Endpoint:** Requests to `/attachments/{uuid}/download` for missing attachments verify division authority and return HTTP 404 with structured error envelope `ERR_404_ATTACHMENT_MISSING`. Zero unhandled exceptions or application crashes.
- **Later Remediation:** Authorized Division Admins can upload a replacement scan via `/attachments/{uuid}/remediate`, updating `file_path`, resetting `is_missing = false`, and setting `migration_status = 'remediated'`.

## F. Single-Division Ownership Decision for v1

### 1. Ratified Decision (`DEC-TEN-001`, `BR-TEN-005`)
In SISURAT v1, **every division-owned record has exactly one owning `division_id`**.

### 2. Specific Implementation Boundaries
- **Ownership Immutability:** `division_id` is assigned upon creation (based on the user's active division context) and cannot be altered through ordinary update forms.
- **Zero Inter-Division Routing:** Features such as cross-division forwarding, letter disposition, and shared multi-tenant ownership are formally classified as `DEFERRED_FUTURE_FEATURE` and will not be built in v1.
- **Super-Admin Scope:** Super Admin viewing of another division's letters does not transfer or mutate ownership.
- **Security Scoping:** Non-super-admin access to records where `letter.division_id != user.division_id` is denied with HTTP 403 Forbidden (`ERR_403_DIVISI`) and audited as `SEC_CROSS_DIVISION_BLOCKED`. Route tampering or payload tampering targeting another division is strictly rejected.

## G. Server-Side Request Idempotency

### 1. Ratified Decision (`DEC-SYS-001`, `BR-IDEM-001`, `IDEM-001`)
Client-side submit-button disabling is an ergonomic user-interface shield, not a data-integrity guarantee. The target system enforces **server-side duplicate submission protection**.

### 2. Technical Specification
- **Header Standard:** High-risk mutation endpoints (`POST /letters/incoming`, `POST /letters/outgoing`, `POST /piagam`) require an `Idempotency-Key` HTTP header containing a client-generated UUIDv4.
- **Persistence Table:** Table 12 (`idempotency_keys`) stores:
  - `key` (UUIDv4 string)
  - `user_id` (bigint unsigned)
  - `route` (varchar 100)
  - `request_hash` (char 64 SHA-256 checksum of normalized request payload)
  - `status` (`in_progress`, `completed`, `failed`)
  - `response_code` (smallint unsigned NULL)
  - `response_body` (mediumtext NULL)
  - `created_at`, `expires_at` (24-hour TTL)
- **Middleware Execution Flow:**
  1. If key does not exist: Reserve key with status `in_progress`. Execute request within `DB::transaction()`. Upon success, cache HTTP 201 response and mark `completed`.
  2. If key exists with matching `request_hash` and status `completed`: Replay cached response immediately without touching application services or persistence.
  3. If key exists with **different** `request_hash`: Return HTTP 409 Conflict (`ERR_409_IDEMPOTENCY_CONFLICT`).
  4. If key exists with status `in_progress`: Return HTTP 409 Conflict (`ERR_409_CONCURRENT_REQUEST`).
  5. If transaction fails: Rollback deletes or marks key as `failed`, allowing safe user retries.
